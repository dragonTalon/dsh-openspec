# Design

## Context

`src/index.ts` registers every skill by iterating the generated `OPENSPEC_SKILLS` array (from `src/skills.ts`) and calling `ctx.skills.register({ name, description, content, source })`. `src/skills.ts` is auto-generated by `scripts/sync-openspec-skills.mjs` from OpenSpec's `skills/*/SKILL.md`; re-running `npm run sync:skills` rewrites the whole file, so any hand edit there is lost. `tests/opsx-skills.spec.ts` currently asserts `summary.description === skill.description` for each canonical skill.

See proposal.md for the motivation (ff vs continue description collision).

## Goals / Non-Goals

**Goals:**
- Give `openspec-ff-change` and `openspec-continue-change` descriptions that unambiguously differ on the batch-vs-incremental axis.
- Keep the override outside the generated file so `npm run sync:skills` cannot clobber it.
- Declare `@deepseek-ai/dsh*` peer ranges that pass the DSH 0.2.x compatibility gate.

**Non-Goals:**
- Re-syncing skill bodies to OpenSpec 1.14.1 (separate change).
- Aligning `devDependencies` to 0.2.x (separate change; only the runtime-checked `peerDependencies` are in scope here).
- Changing the `/opsx-*` alias mapping or the skill `content` bodies.

## Decisions

### D1: Apply the override at registration time in `src/index.ts`

Add a name-keyed description override map in `src/index.ts` and a helper that returns the override when present, otherwise the generated description. `apply()` uses the helper for both the canonical skills and the `/opsx-*` aliases.

**Rationale**: `src/index.ts` is the single registration choke point and is not regenerated. `src/skills.ts` stays pure generated output.

**Alternatives considered**:
- *Edit `src/skills.ts` directly* — simplest, but silently lost on the next `sync:skills`. Rejected.
- *Teach `sync-openspec-skills.mjs` to inject overrides* — couples the routing concern into the content generator; more moving parts for a two-string fix. Rejected for now, can revisit if more overrides accumulate.
- *Fix descriptions upstream in OpenSpec* — correct long-term home, but slow, and OpenSpec 1.14.1's added "Also use when the user says …" hints still do not distinguish ff from continue. Tracked as a follow-up, not this change.

### D2: Description wording

Final wording makes the batch-vs-incremental axis the leading signal and adds a short natural-language routing hint:

- `openspec-ff-change`:
  `Fast-forward OpenSpec artifact creation: generate ALL artifacts for a change in ONE run, without stopping between them. Use when the user wants everything created at once (e.g. "ff" / "fast-forward").`
- `openspec-continue-change`:
  `Continue an OpenSpec change by creating exactly ONE next artifact, then stop. Use when the user wants to step through artifacts one at a time (e.g. "continue").`

**Rationale**: "ALL … in ONE run" vs "exactly ONE … then stop" are the two signals the model must not collapse; the parenthetical hints map natural-language "ff"/"continue" to the right skill.

### D3: Test updates

Export the helper (or the override map) from `src/index.ts`. Update `tests/opsx-skills.spec.ts` to assert the *effective* description (`descriptionFor(skill.name, skill.description)`) instead of the raw generated one, and add explicit assertions pinning the ff/continue wording so a future sync that changes semantics is caught.

### D4: Peer range choice

Set `@deepseek-ai/dsh-skill` and `@deepseek-ai/dsh-invariants` `peerDependencies` to `^0.2.0-rc.2`. Leave `@deepseek-ai/cordis` at `^4.0.1` — the compatibility gate only inspects `@deepseek-ai/dsh*` names, and `^4.0.1` already resolves the 4.0.x used by 0.2.x.

**Rationale**: `^0.2.0-rc.2` satisfies `0.2.0-rc.2` (and later 0.2.x) under `semver.satisfies(…, { includePrerelease: true })`, which is exactly what `evaluatePluginCompatibility` uses. `^0.2.0` (without the prerelease) would NOT match `0.2.0-rc.2`.

**Alternatives considered**:
- *Exact pin `0.2.0-rc.2`* — matches DSH's internal convention but breaks on every future 0.2.x patch. Rejected.
- *`>=0.1.1-rc.2 <0.3.0`* — dual-compatible with 0.1.x and 0.2.x, but the package has already moved to 0.2.x, so the tighter range is clearer. Rejected.

## Risks / Trade-offs

- [A future `sync:skills` pulls upstream wording changes] → the override in `src/index.ts` persists; the explicit wording-pinning tests flag any unintended semantic change.
- [Upstream later fixes ff/continue descriptions, our override shadows the fix] → revisit the override whenever syncing to a newer OpenSpec; the `sync:skills` drift check already cross-checks the alias map.
- [Divergence between the override and upstream description intent] → both descriptions still describe the same workflows; only the routing emphasis changes, not behavior.

## Migration Plan

Rebuild (`npm run build`), then restart the plugin profile. The profile resolves the bundle by `link:` to this repository, so the compatibility gate re-reads the updated `package.json` on the next startup — no reinstall is needed. Rollback is reverting the override map and/or the peer ranges; descriptions fall back to the generated values with no data or schema impact.
